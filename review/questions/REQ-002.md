# REQ-002 Add expense: questions for the requirement owner

Raised while generating tests on 2026-10-20. Drafts assume the app's current behaviour
where the requirement is silent; answers may change review/specs/REQ-002.spec.ts.

**Status: Resolved (2026-10-20).** All 9 questions answered. Rule-defining answers are in
REQ-002's acceptance criteria (scripts/build-requirements.mts) and covered by
review/specs/REQ-002.spec.ts; Q1 and Q9 add no criteria (BUG-004 stays linked).

1. **Client-side validation.** BUG-004 (the form has no client-side validation) is linked
   to REQ-002, but no acceptance criterion requires validation in the browser. Is it
   required? If so: when should it run (on blur or on submit), and should its messages
   match the API's? No tests were written for it until this is answered.
   **Resolved.** **Answer:** Not required for now. Server-side validation is enough,
   keep BUG-004 as a UX improvement for later.
2. **Unstated rules.** The requirement doesn't mention:
   - a maximum title length (the app allows 200 characters)
   - whether a whitespace-only title counts as missing (the app says yes)
   - the allowed categories (the app: Food, Travel, Office, Utilities, Entertainment, Other)
   - the date format and range, e.g. whether future or very old dates are allowed (the app
     accepts any real YYYY-MM-DD date)
   **Resolved.** **Answer:** Keep the app's current rules: title max 200 characters,
   whitespace-only counts as missing, the 6 categories as listed,
   any real YYYY-MM-DD date (no future-date restriction).
3. **Upper bound.** Is 1,000,000 itself allowed? The drafts assume yes ("at most" = inclusive).
   **Resolved.** **Answer:** Yes, 1,000,000 is allowed (inclusive).
4. **Success message and new row.** Should "Expense added" disappear after a while or on
   the next action? Where should the new row appear? The list is currently sorted by date,
   newest first, so a back-dated expense can land far down the list.
   **Resolved.** **Answer:** The message stays until the next action. The new row
   follows the normal date sort, no special position.
5. **Duplicates.** Are two expenses with the same title, amount, category and date allowed?
   **Resolved.** **Answer:** Allowed (people can genuinely buy the same thing twice).
6. **Amount input format.** Should the form accept a thousands separator (`1,000`) or a
   locale decimal comma (`12,50`)?
   **Resolved.** **Answer:** Dot decimal only (12.50); no thousands separator.

## Round 2 (after the criteria update), 2026-10-20

7. **What counts as "the next action"?** Today opening Add or Edit hides "Expense added",
   and a failed delete or export replaces it with the error; changing the category filter,
   a successful Export and Import leave it. Is that intended?
   **Resolved.** **Answer:** Current behaviour is intended. The message clears when the user opens Add or
   Edit, or when another message (e.g. an error) replaces it. Filtering, Export and Import
   don't clear it.
8. **Same-date order.** Expenses on the same date: newest (higher id) first?
   **Resolved.** **Answer:** Yes. Same date: newest first (higher id first).
9. **Comma in the form.** Should the app show its own message when `1,000` or `12,50` is
   typed in the number field?
   **Resolved.** **Answer:** No custom message needed. The browser's number field handling is acceptable in
   the UI; the API rule (scenarios 25–26) is the real check.
